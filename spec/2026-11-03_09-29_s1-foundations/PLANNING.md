## 1. Problem statement

There is no code, repository or tooling. Every later delivery spec (S2–S10) needs:
- a monorepo that builds and tests in CI;
- the full database schema with its integrity rules enforced;
- a lightweight identity, so requests have a user;
- one shared contract package;
- telemetry wired in from the first request.

S1 delivers that foundation and **no product behaviour**: no booking, invites, realtime or UI.

## 2. Context

- [Verified] The project root holds only documentation and specs.
- [Decided 2026-11-03] **The user owns git:** initialising the repository, committing, pushing and creating the GitHub remote. Claude never commits or pushes (`CLAUDE.md`).
- [Verified] The stack and structure are fixed by the parent plan (§5, §6): Bun + Hono, PostgreSQL, Kysely on postgres.js, Zod contracts, OpenTelemetry → Grafana Cloud, GitHub Actions.
- [Verified] The data model is fixed by the parent plan §4.3, plus `communities` (Q11) and `bookings.ref` (UX-2).

## 3. Desired outcome

From a fresh checkout, two commands give a working foundation:
1. `bun install && docker compose -f infra/docker-compose.yml up -d`
2. `bun run db:migrate && bun test`

The result:
- an empty-but-complete schema whose insert-only and immutability rules are enforced by Postgres;
- an API that serves `/api/healthz`, `/api/readyz`, `POST /api/sessions` and `GET /api/me`;
- telemetry visible in the local collector;
- CI green on every push.

### 4.3 Database

- **Postgres** [Decided 2026-11-03]: the official `postgres` image at the **latest stable release**, checked at implementation time and pinned by exact tag (for example `postgres:<major>.<minor>`, never `latest`). The parent plan's floor of 16 is satisfied.
- **Migrations** [Decided 2026-11-03]: **dbmate**, latest stable, pinned by image tag. These are plain forward-only `.sql` files run from its container image, so there's no custom runner to maintain. Each migration runs in a transaction.
- **Roles** (created by the first migration):
  - `velio_owner` owns the schema; migrations run as it.
  - `velio_api` is the runtime role: `SELECT, INSERT` on insert-only tables; `SELECT, INSERT, UPDATE` on mutable tables; no `DELETE` anywhere except `sessions` and `rate_limits`.
  - `velio_readonly` has `SELECT` only, for metrics views (S8).
- **Tables:** all tables from the parent plan §4.3, including `communities`, `bookings.ref`, the hash-chain columns (`prev_hash`, `row_hash`; computed in S4) and `rate_limits` (§4.7 of the parent).
- **Constraints, all in S1:**
  - checks: `spots_left` between 0 and `capacity`; `capacity` ≥ 1; positive price and `currency` as ISO 4217 text; `timezone` must be a valid IANA zone (check against `pg_timezone_names` via trigger); `lat` between -90 and 90 and `lng` between -180 and 180 (`numeric(9,6)`); `venue_name` and `address_text` non-empty; `meeting_point` at most 140 characters (Google Maps spec §5.1).
  - partial unique indexes: one confirmed booking per user per activity; one claim per vouch.
  - unique `invites.code`, `bookings.ref`, `attributions.invitee_id`, `(user_id, idempotency_key)`.
- **Integrity triggers:**
  - `forbid_update_delete()` on every insert-only table (`invites`, `invite_claims`, `attributions`, `trust_edges`, `attendance_marks`, `booking_removals`);
  - `users.invite_generation` immutable after insert;
  - `users.created_at` immutable;
  - `activities` location lock: an UPDATE that changes `starts_at`, `timezone`, `place_id`, `venue_name`, `address_text`, `lat`, `lng` or `meeting_point` raises `location_locked` when the activity has a confirmed booking (PRD Q2, Q13).
- **Reference data:** a data migration seeds the three communities (Explore Kenya, The Tanzania Experience, The Medina Collective). Cover photos are placeholders until S5.
- **Types:** `kysely-codegen` generates `db/types.ts` from the migrated database. CI fails if it is stale.

### 4.4 Identity (lightweight, per PRD non-goals)

- `POST /api/sessions` takes `{ displayName, contact }` and returns `{ user: MemberPerson, token? }`.
  - Normalise the contact: email is trimmed and lowercased; phone is converted to E.164 with `libphonenumber-js`.
  - Find a user by `contact_hash`, or create one with `invite_generation = 0` (organic).
  - Create a session and set an httpOnly, Secure, SameSite=Lax cookie `velio_session`. Clients that send `X-Client: mobile` instead get the token in the response body, for the `Authorization: Bearer` header.
- **Contact hash:** `HMAC-SHA256(CONTACT_PEPPER, normalised)`. A per-row salt would make matching (R5) impossible, so the "salted hash" in the parent plan is realised as a keyed hash with a server secret. [Proposal: clarifies parent §4.6]
- **Session tokens:** 32 random bytes, base64url. Only the SHA-256 is stored.
- **Session lifetime** [Decided 2026-11-03: industry standard, following the OWASP Session Management Cheat Sheet and ASVS]:
  - **Idle timeout, 30 days, sliding:** each authenticated request at least 24 h after the last renewal extends `expires_at`. Throttling the renewal avoids a write on every request.
  - **Absolute timeout, 90 days** from creation. After that the user signs in again, whatever their activity.
  - **Server-side check on every request.** An expired session is treated as missing (`401 unauthenticated`), and a scheduled job deletes expired rows (S1 adds the query; the scheduler arrives with the jobs in S8).
  - **Rotation:** `POST /api/sessions` always issues a new token. An existing session cookie sent with that request is revoked, which prevents session fixation.
  - **Cookie** `Max-Age` matches the idle timeout and is refreshed on renewal. Mobile bearer tokens follow the same server-side rules.
  - **Revocation:** `DELETE /api/sessions/current` signs the user out (deletes the row, clears the cookie).
  - **Why these numbers:** OWASP sizes timeouts by risk. Velio holds no payments and identity is unverified (parent SEC-008), so this is a low-risk consumer app where long-lived, revocable "remember me" sessions are standard. The values are config (`SESSION_IDLE_DAYS`, `SESSION_ABSOLUTE_DAYS`), not hard-coded.
- `GET /api/me` returns the current `MemberPerson`, or `401 { error: { code: "unauthenticated" } }`.
- **Auth middleware** resolves the user on every request. Routes declare `public` or `authenticated`.
- **Limitation:** identity is unverified (SEC-008 in the parent).

### 4.5 Contracts

`packages/contracts` exports Zod schemas, and from them TypeScript types:
- `ErrorEnvelope`, the complete typed error-code union from parent §4.4 plus `location_locked` (Google Maps spec), so later specs only use codes;
- `PublicPerson` and `MemberPerson`;
- `SessionCreate` and `SessionResponse`;
- `Health`.

The API mounts routes with `@hono/zod-openapi`, and `bun run contracts:openapi` writes `openapi.json`. CI regenerates it and fails on any difference. Dart client generation starts in S7.

### 4.6 Telemetry base

- **Step 1 is a spike** (§6, T3): confirm on the current Bun that the OpenTelemetry JS SDK (trace and metric providers with OTLP/HTTP exporters) and `@hono/otel` work. Record the result in this spec's change log.
  - **Fallback:** hand-written Prometheus-format metrics at `/api/metrics` (internal only), scraped by the collector, with tracing deferred. The fallback needs user approval if it's taken, because it changes the parent design.
- **Instruments in S1:**
  - `http_server_duration_seconds` (route template, method, status class);
  - `db_pool_in_use`;
  - query spans around Kysely calls (operation name only, never parameters).
- **Logger:** structured JSON (pino) with `trace_id` and `request_id`. Redaction removes `contact`, `token`, `authorization`, `cookie`, `note` and `code` keys, and invite codes in paths matching `/i/:code` or `/invites/:code`.
- **Local collector:** OTLP receiver plus a debug exporter to stdout. Setting `GRAFANA_OTLP_*` env vars enables the Grafana Cloud exporter; it is off by default locally. Production wiring is S10.

### 4.7 Configuration

- `config.ts` parses `process.env` with Zod at boot and exits with a clear message if anything is missing.
- Variables: `DATABASE_URL` (velio_api), `DATABASE_LISTEN_URL` (direct connection for S3), `CONTACT_PEPPER`, `ORIGIN_VERIFY_SECRET` (enforced only when `NODE_ENV=production`), `OTEL_EXPORTER_OTLP_ENDPOINT`, `LOG_LEVEL`.
- `.env.example` documents each one. No secrets are committed.
- Google Maps keys and the Static Maps signing secret are **not** S1 configuration. They are added by the first spec that uses them (S2 or S5 for the snapshot's signed map URL; S10 for production secrets).

### 4.8 CI (`.github/workflows/ci.yml`)

On every push and pull request:
1. `oven-sh/setup-bun` → `bun install --frozen-lockfile`.
2. `prettier --check`, `eslint`, `tsc --noEmit`.
3. Start a Postgres service container → `dbmate up` → check that kysely-codegen output is unchanged.
4. `bun test` (unit and integration against the real Postgres).
5. Check that `contracts:openapi` output is unchanged.

Target: under 5 minutes [Assumption].

## 5. Architectural considerations

- **Errors:** one place maps errors to the envelope. Unknown errors become `{ code: "internal" }` with a `request_id`, and never a stack trace.
- **Routing:** every route lives under `/api` (parent §4.8).
- **WebSocket:** `index.ts` already passes `websocket` to `Bun.serve`, but S1 registers no WebSocket routes. That keeps S3's change additive.
- **Bun-only code** is limited to `index.ts` and, later, `modules/realtime` (parent §8).

## 8. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| OTel SDK doesn't work on Bun | T3 runs first. The fallback is defined in §4.6 and needs approval before it's used. |
| Schema decisions made now are wrong for S2–S4 | Only constraints already specified in the parent plan are added. Later changes are new forward-only migrations. |
| Codegen or OpenAPI drift between developers | Both are checked in CI. |
| `pg_timezone_names` check in a trigger is slow | It runs only on activity insert or update, which is rare. |

## 9. Alternatives considered

- **Kysely Migrator with TypeScript migrations:** keeps everything in TypeScript, but the parent chose plain SQL, and dbmate needs no custom code.
- **Node's `pg` driver:** postgres.js is chosen for its proven Bun support and LISTEN (parent §5).
- **Bun's built-in `Bun.sql`:** not used until LISTEN support is verified (parent §10).
