### Added

The README now follows the brief: quick start, architecture and decisions, plan vs. reality, trade-offs and where to see the tracking. The AWS operations runbook moved unchanged to `infra/aws/README.md`.
- A specification-driven development process: the project constitution (`CLAUDE.md`), a roadmap (`ROADMAP.md`), this changelog with its maintenance skill, and the `spec/` directory for timestamped specifications. No application functionality exists yet. ([spec](spec/2026-11-03_07-25_establish-sdd-constitution/))
- The Velio design system and the complete Group Bookings UI in Claude Design: tokens and 29 components (including Google Maps location, picker and community map components), and 42 high-fidelity screens covering guest, booker, host, community, profile, account, error and admin flows on web (phone and desktop) and Flutter, with responsive rules for 360px to desktop and text scaling to 200%. Source is saved with the spec. ([spec](spec/2026-11-03_10-34_complete-ui-design/))
- The application foundation (S1): a Bun workspace with the API and a shared contracts package. Two commands set it up from a fresh clone. Local Docker Compose runs Postgres, MinIO and an OpenTelemetry Collector. The complete database schema is applied by forward-only migrations: insert-only tables reject updates and deletes for every role, user generation and creation time can't change, activity values are range-checked, and an activity's date and location lock after its first confirmed booking. The three communities are seeded. "Continue as" sign-in takes a name and an email or phone. Contacts are normalised and stored only as a keyed hash; web clients get a cookie and mobile clients a bearer token; sessions expire after 30 days idle or 90 days total, rotate on sign-in and support sign-out. Health and readiness endpoints, typed error envelopes and generated OpenAPI are in place. Traces, metrics and JSON logs share a trace ID, with personal data and invite codes redacted. A GitHub Actions CI workflow runs format, lint, types, migrations, drift checks and tests. It hasn't run on GitHub yet. ([spec](spec/2026-11-03_09-29_s1-foundations/))
- The booking core (S2). Hosts can create activities and edit them, including capacity: raising it reopens a sold-out activity, it can't go below the confirmed bookings, and date, time zone and location lock after the first booking. People can book a spot directly. Each booking creates their Plan and a `VLO-` reference, and a booking either takes exactly one spot or fails with a typed reason (`sold_out`, `already_booked`, `activity_started`, `bookings_paused` and others). Retries with the same `Idempotency-Key` return the original booking. Hosts can remove an attendee, which frees the spot at once, and a removed person can't book that activity again. Overselling is prevented in the database. A concurrency test in `bun test` fires 200 parallel bookers at 1, 5 and 14 spots and gets exactly N bookings, and `bun run load:smoke` repeats the race through k6. Every change to the spot count bumps a version and sends a Postgres notification for S3. Booking metrics and a post-booking oversell check are recorded. CI on GitHub hasn't run it yet. ([spec](spec/2026-11-03_22-30_s2-booking-core/))
- Live updates (S3). `GET /api/activities/:id` is a public snapshot of an activity: details, live spots left with a version, open / sold out / started, host and members shown as "Tunde A.", a Google Maps directions link, and the signed-in viewer's own booking. A WebSocket at `/api/ws` delivers every committed change to spots left to anyone watching the activity, in version order and only after the transaction commits, plus "refetch" hints to Plan members and to the host's attendance view. If the API's database listener drops, it reconnects and tells every client to refetch, and readiness reports unavailable meanwhile. Clients acknowledge what they render, so the PRD's commit-to-screen latency is a metric. Client rules (subscribe, then fetch; ignore older versions; poll every 10 s while disconnected) are documented in the contracts package for the web and mobile apps. `bun run load:viewers` holds 250 sockets on one activity during a last-spot race: p95 47 ms locally. The static map image isn't signed yet (S6). ([spec](spec/2026-11-04_11-42_s3-realtime/))
- Invites, claims and attribution (S4). Anyone going can invite from their Plan: a vouch addressed to one named friend (single use; the contact is kept only as a keyed hash, never raw) or their public link (multi use). Each invite has a 6-character code and a link. Its public page shows the inviter as "Tunde A.", the note and the live activity. A beacon records one open per device after the page renders, ignoring link-preview bots and the Plan's own members. A claim is a booking through the same engine: a new guest is signed in and joins the inviter's Plan in one transaction, with their inviter and generation fixed forever by the first claim, and a later vouch for someone already on Velio is kept as a trust edge. Two people claiming one vouch at once get one booking. Attribution and invites are hash-chained per activity in the database, and `audit_chain` finds any edited or deleted row. A device that tries more than 10 unknown codes in an hour is locked out of every code until the hour ends. Public links take at most 60 claim attempts a minute, pause themselves when 200 opens in an hour bring under 2% claims, and can be paused by their creator or the host. Read APIs for the apps: the Plan view (members, how each joined, invite status, live), My plans, the host's activity list, attendance with attended or no-show marking after the start, communities with their upcoming activities, profiles, and the "host's other dates" and "More in [community]" suggestions. Holdout gating is still to come (S8). ([spec](spec/2026-11-04_11-42_s4-invites-attribution/))
- The web app (S5), a Next.js app on the approved Velio design system, served by the same CloudFront hostname as the API. Booker: community pages with a list and a Google map, activity pages with live spots, a map that loads on tap and directions, booking with the sold-out-mid-checkout, already-booked, started and paused states, the post-booking invite step, vouch invites (sent from your own WhatsApp or SMS; the friend's contact goes only to the API) and the shared link with pause and resume, the Plan with members, how each joined and invite statuses updating live, My plans, profiles and sign-out. Host: a Booker / Host toggle, the activity list with "Mark attendance" after the start, create and edit with a photo upload (straight to S3, two WebP sizes made in the browser), Google Places search with a draggable pin and a no-maps fallback, locked date and place after the first booking, and live attendance: new bookings appear as they land, the groups summary, removal with confirmation (the spot frees on every screen at once), attended or no-show after the start, and guest search by name or booking ref on phone. Guests and non-members see short names ("Tunde A."); hosts see names, refs and sources, never contacts. Layouts hold from 360 px to desktop. Host and booker flows pass end to end on the deployed stack, with live updates over the WebSocket through CloudFront and photo uploads to S3. No accessibility audit yet (S9). ([spec](spec/2026-11-04_12-50_s5-web-host-booker/))
- The Flutter app for iOS and Android (S7), on the shared design tokens and fonts. A guest types a 6-character code (case and spaces forgiven; unknown codes shown inline, a rate-limited device told to wait) or follows an invite link, sees the invite with live spots over the WebSocket, the host, who's going as short names, the price and the location with directions, and claims in one step: two fields the first time, "Claiming as {Name} · {masked contact}" with "Not you?" after. Each claim attempt keeps one idempotency key, so a retry never books twice. Success gives a haptic and "You're in" with the booking reference and the group; sold out gives a different haptic and the next steps. Expired, claimed, paused and already-going invites have their own screens. The Plan shows members, how each joined and invite statuses live, and "Invite a friend" creates a vouch or opens the public link and hands it to the phone's share sheet. My plans lists upcoming and past Plans; sign-in brings them to a new phone; profiles and error screens are included. The last invite and My plans are saved on the phone and shown offline with when they were updated, while Claim waits for the network (nothing is queued). The session token and device ID are in the platform's secure storage, and only a masked contact is kept. A Dart API client is generated from the OpenAPI document (`bun run contracts:dart`), and a CI job checks it for drift and runs `dart format`, `flutter analyze` and the tests, which render every screen at 360 px and at 200% text. The app completes the claim flow against the deployed stack on the iOS simulator and on an Android phone, and invite links open the app directly on Android (verified App Links). Not yet: native maps (they need the owner's mobile Maps keys; the address and directions show instead), and hands-on checks for haptics, screen readers and airplane mode. ([spec](spec/2026-11-04_12-50_s7-flutter-app/))

- The Flutter app now does everything the web app does (S7b). A Booker / Host toggle, remembered on the phone, sits in the app bar; bookers get bottom tabs for Explore, Code and My plans, and the app still opens on code entry. Bookers browse a community with live spots (and a native map when Maps keys are set), open an activity page and book a spot. Each attempt keeps one idempotency key, so a retry books once at most, and success or sold out gives a haptic. Every state the web shows is covered: host, already going, removed, started, paused, sold out, signed out and offline. Hosts get My activities (upcoming and past, with "Mark attendance"), create and edit with a photo (cropped to 16:10, sent to S3 as 1280 px and 640 px JPEGs, with none of the app's headers), Places search when a `PLACES_KEY` is set, a native pin when Maps is on, typed coordinates otherwise, and the web's validation and locked fields after the first booking. Live attendance shows new bookings as they land, removal with confirmation, attended or no-show from the start, and search by name or ref. Activity links in next steps, Plans and profiles now open in the app. On the iOS simulator against the local API, a person books from Explore, then as host publishes an activity with a photo, sees a second person's booking arrive live, and removes it. Not yet: Places search and native maps on a real key, and a run against the deployed stack. ([spec](spec/2026-11-04_23-59_s7b-flutter-web-parity/))
- The Flutter community map now has a swipeable row of preview cards along its lower edge, one per pin. Each card shows the activity's photo, title, date and venue, a short description, price and live spots. Tapping a pin highlights it and scrolls to its card; swiping to a card pans the map to its pin; tapping a card opens the activity. The first view fits every pin. To support this, activity cards from the API (community pages, My plans, profiles, next steps, host lists) now include `summary`: the description's start, cut at a word to at most 140 characters. The map behaviour hasn't been tried on a simulator yet. The API change is deployed. ([spec](spec/2026-11-05_08-02_explore-map-preview/))
- Metrics, the holdout and an admin page (S8). Invites now run behind the PRD's `group_invites` holdout: a stable 10% of users never get invite tools, enforced by the API (`canInvite: false` and `403 invites_unavailable`), so web and the app needed no change. Each user's arm is logged the first time they reach invite tools. The funnel now also records claims, server errors and activity views, and the web reports real-user Web Vitals. SQL views compute every PRD success metric. `/admin` on the web, behind a generated admin token, shows the five goals against their targets and triggers, the funnel and K-factor per rail, the plans-happen guardrail and the holdout split. It also runs the attribution audit and pauses or resumes bookings for any activity. The API checks for oversold activities every 5 minutes and audits every hash chain nightly. Three Grafana dashboards and four alert rules (oversell, booking success, live-update p95, broken chain) live in `infra/grafana/` with a push script. The dashboards and alerts are pushed to Grafana Cloud and show production only (telemetry now carries `deployment.environment`), and the alerts email a dedicated contact point. Deployed and checked through CloudFront: `/admin` data answers in about 0.55 s, and the production oversell gauge reads 0 in Grafana. Pausing doesn't push to open pages; they show it on their next load or booking attempt. ([spec](spec/2026-11-05_08-36_s8-metrics-flags-admin/))

### Fixed
- On the web at phone width, activity cards with a real photo no longer break: the photo used to overflow its box, cover the card's title and run into the next card. Photos in activity cards and in Plan and next-step thumbnails now fill and crop to their box like the placeholder art. Not deployed yet. ([spec](spec/2026-11-05_10-55_web-card-photo-overflow/))
- Booking duration, spot row wait and HTTP latency histograms now have explicit buckets. Before, OTel's default boundaries put every request in the first bucket, so their p95 always read about 4.75 s in Grafana. Live in production. ([spec](spec/2026-11-05_08-36_s8-metrics-flags-admin/))
- The Flutter app's live connection now carries the signed-in person's session and reconnects when they sign in or out. Before this, the socket was always anonymous, so a Plan's invite statuses on the phone updated only when the screen refetched. ([spec](spec/2026-11-04_23-59_s7b-flutter-web-parity/))

### Changed
- The Flutter app is rebuilt on `flutter_bloc` with the official layered bloc architecture, replacing Riverpod; what people see and do is unchanged. The code is organised by feature. Data providers wrap the API, socket, cache and secure storage. Repositories expose domain operations and live-update streams. A bloc per screen holds all the logic, and widgets only render state and send events. Every widget class is public. Each bloc has its own `bloc_test` suite, and the existing widget tests run unchanged on a new harness (289 test runs pass). On the iOS simulator against the local API, the booking, hosting and live attendance test passes. The claim smoke test passes against the deployed stack. This work also fixed a code-entry layout error: with the keyboard open, the typed code could be lost. ([spec](spec/2026-11-05_00-40_flutter-bloc-refactor/))
- Activity photos are now cropped to 16:10 around the centre when a host uploads them (every screen already showed them that way) and encoded at a lower quality, and phones load the 640 px version on activity and invite pages. A real photo's phone file drops from 110 kB to 45 kB. Photos uploaded earlier are unchanged. ([spec](spec/2026-11-04_12-50_s6-web-invite-claim/))
- Product requirements now state that a vouch invitee's raw contact is never stored, only its keyed hash (PRD Q7), because invites are sent from the booker's own phone. ([spec](spec/2026-11-04_11-42_s4-invites-attribution/))
- Product requirements now state that a person the host removed can't book that activity again (the host's other dates stay open to them). ([spec](spec/2026-11-03_22-30_s2-booking-core/))
- Product requirements now include Google Maps locations (host place search and pin, maps with directions, community map, meeting point) and a My plans screen; the MVP plan and S1 schema were updated to match. ([spec](spec/2026-11-03_10-34_google-maps-locations/))
